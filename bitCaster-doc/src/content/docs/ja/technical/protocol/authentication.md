# 認証

bitCasterは、すべてのトレード関連APIリクエストを[NIP-98](https://github.com/nostr-protocol/nips/blob/master/98.md) HTTP Authで認証します。注文の発注、マーケットの作成、支払いインボイスのリクエストなど、すべての書き込みリクエストには、呼び出し元のNostr秘密鍵で署名された有効なNIP-98認証ヘッダーが必要です。

読み取り専用エンドポイント（オーダーブックのスナップショット、マーケットメタデータ、価格フィード）はパブリックのままで、認証は不要です。

## NIP-98の仕組み

NIP-98は、各HTTPリクエストを暗号的に署名されたステートメントに変換します：*「公開鍵 `X` の所有者である私が、この瞬間にこの特定のリクエストを行っています。」*

フロー：

1. **クライアントがkind `27235`のNostrイベントを作成**し、2つのタグを付与：
   - `["u", "<リクエストの絶対URL>"]` — トークンをこの正確なURLに紐付け
   - `["method", "<HTTPメソッド>"]` — トークンをGET、POST、DELETEなどに紐付け

2. **クライアントがイベントに署名** — BIP-340 Schnorr署名を使用（Nostrがすべてのイベントに使用するものと同じ方式）。署名により、対応する秘密鍵の所有権が証明されます。

3. **クライアントがヘッダーを送信：**
   ```
   Authorization: Nostr <署名済みイベントのJSONをbase64urlエンコードしたもの>
   ```

4. **サーバーが検証：**
   - イベントkindが `27235` であること
   - タイムスタンプが±60秒以内（リプレイ防止）
   - URLタグが正確なリクエストURLと一致
   - メソッドタグがHTTPメソッドと一致
   - イベントIDがNIP-01のSHA-256ハッシュと一致
   - BIP-340 Schnorr署名が有効であること

5. **サーバーがイベントから公開鍵を抽出**し、リクエストの認証済みIDとして使用します。

## リクエスト署名の例

`POST /api/v1/deadbeef01-Alice/orders` に注文を送信する場合、クライアントは以下を構築します：

```json
{
  "id": "<シリアライズされたイベントのSHA-256>",
  "pubkey": "a1b2c3d4e5f6...64桁の16進数...",
  "created_at": 1713600000,
  "kind": 27235,
  "tags": [
    ["u", "https://engine.bitcaster.market/api/v1/deadbeef01-Alice/orders"],
    ["method", "POST"]
  ],
  "content": "",
  "sig": "<BIP-340 Schnorr署名...128桁の16進数>"
}
```

イベントはJSONにシリアライズされ、base64urlエンコードされ、以下の形式で送信されます：

```
Authorization: Nostr eyJpZCI6Ii4uLiIsInB1YmtleSI6Ii4uLiIsImNyZWF0ZWR...
```

各リクエストには新しいトークンが必要です。タイムスタンプとURLの紐付けにより、トークンの再利用はできません。

## エンドポイント認証要件

| エンドポイント | 認証 | 理由 |
|----------|------|-----|
| `POST /{marketId}/orders` | 必須 | 注文の所有権を確立 |
| `DELETE /{marketId}/orders/{orderId}` | 必須 | 所有者のみキャンセル可能 |
| `GET /{marketId}/orders/{orderId}` | 必須 | 所有者のみステータス照会可能 |
| `POST /markets/{conditionId}` | 必須 | 作成者のIDは認証から取得 |
| `POST /markets/{marketId}/payment-requests` | 必須 | IDごとにレート制限 |
| TradeHub (`/hubs/trade`) | 必須 | 取引相手の検証 |
| `GET /{marketId}/orderbook` | 公開 | 読み取り専用のマーケットデータ |
| `GET /{marketId}/liquidity` | 公開 | 読み取り専用のプール状態 |
| `GET /{marketId}/metadata` | 公開 | 読み取り専用のマーケット情報 |
| MarketHub (`/hubs/market`) | 公開 | リアルタイム価格フィード |

## 二重鍵モデル

bitCasterは2種類の鍵を使用します：

**メインNostr鍵** — ユーザーのBIP-39ニーモニックから導出されます。これはHTTPエンドポイントでのNIP-98認証に使用される長期的なIDです。マッチングエンジンはこの公開鍵を注文の所有権管理とレート制限のための`UserId`として使用します。

**エフェメラル（一時）鍵** — `secp256k1.utils.randomSecretKey()`を使用して注文ごとに生成される新しいsecp256k1鍵ペアです。公開鍵部分は注文とともにマッチングエンジンに送信されます。マッチ後、エンジンは両当事者のエフェメラル公開鍵を中継し、暗号化されたアトミックスワップ通信のためのECDH共有秘密を確立できるようにします。

TradeHub（SignalR）はエフェメラル鍵をNIP-98認証に使用します — 取引相手はメインのNostr IDを知ることはありません。ミントもエフェメラル鍵で署名されたP2PK支出のみを確認するため、取引を永続的なIDに紐付けることはできません。

この分離により、注文管理には安定したID（キャンセル、レート制限用）を使用しつつ、取引決済では匿名性を保持します。

## エラーレスポンス

| ステータス | 意味 |
|--------|---------|
| **401 Unauthorized** | NIP-98トークンが欠落、不正、または期限切れ |
| **403 Forbidden** | 有効なトークンだが、認証されたユーザーがリソースを所有していない（例：他のユーザーの注文をキャンセルしようとした場合） |

## 将来の認証方法

マッチングエンジンは、NIP-98以外の追加の認証スキームをサポートするように設計されています。アーキテクチャはASP.NET Coreのネイティブなマルチスキーム認証を使用しており、新しいスキーム（LN-authなど）をエンドポイントコードを変更せずに追加できます。すべてのスキームは同じ標準IDクレームを発行するため、エンドポイントはスキームに依存しない単一のヘルパーを通じて認証済み公開鍵を抽出します。
